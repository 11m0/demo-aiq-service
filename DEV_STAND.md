# Локальный дев-стенд

Каталог проекта: `C:\work\my_proj_1\aisto-demo-ai-service`.
Все команды ниже выполняются из него. После переименования откройте в IDE новый
каталог и выберите его `.venv` как интерпретатор. Внутренние имена Python-пакетов
`questionnaire_*` сохранены. При переносе на другую машину создавайте окружение
через `scripts/setup_dev.py`, не копируйте `.venv` и `node_modules`.

Три процесса на одной машине: браузер → Vite `/api` → Backend → ML API → LLM.
Поддержан запуск на Windows и Linux. Backend и ML слушают только `127.0.0.1`;
межсервисный Bearer-токен остаётся в Python-процессах. Браузер использует относительные
адреса `/api`, поэтому CORS и адрес ML в браузере не нужны.

## Подготовка

Нужны Python **3.12**, Node.js **>=22.12**, pnpm **11.19.0** в PATH, доступ к
реестрам Python/npm при установке и к HTTPS endpoint провайдера LLM при работе.
Docker, GPU, БД и отдельная загрузка весов модели не требуются: ML обращается к
внешнему Responses-совместимому API с поддержкой JSON Schema structured output.
На Linux должен быть доступен модуль `venv` для Python 3.12.

Из корня проекта на Windows:

```powershell
py -3.12 scripts/setup_dev.py --env-file .env.dev
```

На Linux:

```bash
python3.12 scripts/setup_dev.py --env-file .env.dev
```

Скрипт создаёт `.venv`, устанавливает `requirements.lock.txt`, проверяет зависимости,
выполняет `pnpm install --frozen-lockfile` и `pnpm build` в `Frontend`.
Версии пакетов берутся из lock-файлов; установка не обновляет их.
Повторный запуск разрешён. Существующий файл настроек сохраняется. Новый файл
получает случайный `SERVICE_AUTH_TOKEN`, который скрипт не печатает.
Файлы `.env.*` исключены из Git; не пересылайте их с исходниками или журналами.
На Linux новый файл создаётся с правами `0600`; на Windows используются ACL каталога.

Заполните `.env.dev` в редакторе:

| Настройка | Назначение |
| --- | --- |
| `APP_ENV=dev` | Для рабочего стенда требует настройки LLM. `local` допускает health-only. |
| `SERVICE_AUTH_TOKEN` | Общий токен Backend и ML; генерируется при подготовке. |
| `LLM_API_KEY` | Ключ провайдера, только на сервере. |
| `LLM_MODEL` | Идентификатор доступной у провайдера модели. |
| `LLM_BASE_URL` | HTTPS базовый URL Responses-совместимого API; пусто для стандартного endpoint клиента. |
| `LLM_TIMEOUT_SECONDS=60` | Таймаут одного обращения к модели. |
| `ML_TIMEOUT_SECONDS=200` | Бюджет Backend; должен быть больше `3 * LLM_TIMEOUT_SECONDS`, максимум 390. |
| `BACKEND_SESSION_TTL_SECONDS=3600` | Время жизни сессии в памяти. |
| `BACKEND_MAX_SESSIONS=1000` | Лимит хранимых сессий. |

Остальные лимиты и ротация токена описаны в `.env.example`. Системные переменные
окружения имеют приоритет над выбранным файлом. При `--env-file` настройки из
корневого `.env` не подмешиваются. Для раздельного запуска сервисов можно задать
`QUESTIONNAIRE_ENV_FILE` абсолютным путём до импорта приложения.

## Запуск и остановка

Windows:

```powershell
.\.venv\Scripts\python.exe run.py --env-file .env.dev --check
.\.venv\Scripts\python.exe run.py --env-file .env.dev
```

Linux:

```bash
.venv/bin/python run.py --env-file .env.dev --check
.venv/bin/python run.py --env-file .env.dev
```

`--check` проверяет Python, наличие Vite, версию Node, настройки обоих сервисов,
бюджет таймаутов и свободные порты. Он не проверяет доступность LLM и не поднимает
серверы. При обычном старте компоненты последовательно проходят HTTP readiness.
Если компонент завершится или не станет готов, launcher остановит остальные.
`Ctrl+C` останавливает весь стенд; на Linux также обрабатывается `SIGTERM`.
На Windows закрытие launcher завершает дочерние процессы через Job Object.
Launcher работает на переднем плане: для постоянной работы на стенде потребуется
настройка сервисного менеджера под конкретную ОС.

| Компонент | Адрес по умолчанию |
| --- | --- |
| Интерфейс | `http://127.0.0.1:5173` |
| Backend | `http://127.0.0.1:8001` |
| ML API | `http://127.0.0.1:8000` |

Порты можно изменить одной командой, например:

```bash
.venv/bin/python run.py --env-file .env.dev --api-port 18000 --backend-port 18001 --frontend-port 15173
```

Launcher автоматически согласует `ML_TURN_URL` и `VITE_BACKEND_TARGET` с портами,
переопределяя их для этого запуска. Занятые порты дают ошибку, чужие процессы не
останавливаются. Для раздельного запуска используйте прежние скрипты API/Backend
и `pnpm dev`; там адреса нужно согласовать вручную.

Без ключа модели оставьте `APP_ENV=local` и все `LLM_API_KEY`, `LLM_MODEL`,
`LLM_BASE_URL` пустыми, затем добавьте `--health-only`. Сервисный токен всё равно
нужен Backend. В этом режиме доступны интерфейс и сессии, обработка реплик через
LLM недоступна. Флаг не отключает настроенную модель.

## Проверка работоспособности

Во втором терминале из корня проекта:

```powershell
.\.venv\Scripts\python.exe scripts/smoke.py
```

На Linux замените путь интерпретатора на `.venv/bin/python`. Для изменённых портов
передайте smoke-скрипту те же `--api-port`, `--backend-port`, `--frontend-port`.

Проверяются `/health/live` и `/health/ready` обоих Python-сервисов, отказ ML без
токена, HTML интерфейса, создание/чтение сессии через прокси Vite, выбор сценария,
удаление сессии и ответ 404 после удаления. Проверка не вызывает LLM и работает
в health-only. Созданная сессия удаляется в `finally`, включая ошибку полного хода.
Код завершения 0 означает успех, ненулевой — ошибку.

Для полного маршрута Frontend → Backend → ML → провайдер:

```powershell
.\.venv\Scripts\python.exe scripts/smoke.py --live
```

Этот режим отправляет синтетическую реплику и расходует квоту провайдера.
Он требует успешного обновления сессии; контролируемый отказ ML считается ошибкой.
Health/readiness подтверждают инициализацию, а не валидность ключа или доступность
модели. Для подтверждения этих свойств нужен `--live`.

Регрессионная проверка:

```powershell
.\.venv\Scripts\python.exe -m pytest -q
.\.venv\Scripts\python.exe -m ruff check .
pnpm --dir Frontend build
```

`dev_tests` добавлен в общий запуск pytest. Он проверяет lifespan readiness,
занятые порты, очистку частичного запуска, отдельный файл окружения, health-only,
таймауты и отсутствие секретов в ошибках preflight.

## Доступ с другой машины

Для одиночного удалённого стенда с SSH достаточно туннеля:

```bash
ssh -N -L 5173:127.0.0.1:5173 user@dev-host
```

После этого откройте `http://127.0.0.1:5173` на своей машине. ML и Backend не нужно
публиковать в сеть. `user@dev-host` замените учётной записью и адресом стенда.
Для общего доступа по DNS нужна отдельная настройка HTTPS reverse proxy и контроля
доступа с учётом ОС и адреса стенда. Публиковать существующий API сессий напрямую
в общедоступную сеть нельзя: пользовательской авторизации пока нет, знание
`sessionId` даёт доступ к соответствующей сессии. Сервисный токен защищает только ML.

## Эксплуатационные ограничения и диагностика

- Backend хранит сессии в памяти. Перезапуск теряет анкеты; используется ровно один
  worker и один экземпляр Backend. Не задавайте несколько workers через supervisor.
- Frontend обслуживается Vite dev-сервером. `pnpm build` проверяет сборку, но launcher
  не раздаёт `dist`. Для production требуется отдельная схема публикации статики.
- HTTP к ML разрешён только через loopback. Для разнесения сервисов по машинам
  требуется HTTPS; проверки безопасности URL сохранены.
- При ошибке настройки preflight выводит имена полей, а не их значения. Проверьте
  выбранный файл и переменные среды, не копируя секреты в терминал или чат.
- Ошибка порта: остановите свой предыдущий стенд или выберите другой набор портов.
- Health успешен, а `--live` нет: проверьте доступ к провайдеру, модель, поддержку
  Responses/structured output, квоту и настройки таймаутов. Журналы сервисов идут
  в консоль; сопоставляйте ход по `correlation_id`.
- Не увеличивайте таймаут LLM без согласования Backend. Vite ждёт upstream до 400
  секунд, что покрывает максимальный разрешённый бюджет Backend 390 секунд.

На машине подготовки проверены Windows-запуск трёх процессов с отдельным файлом
окружения и нестандартными портами, smoke без LLM, сборка Frontend и Python-тесты.
Linux-ветка и реальный провайдер должны быть проверены на целевом стенде.
