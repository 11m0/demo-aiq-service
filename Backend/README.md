# Backend

Серверный BFF связывает браузерный интерфейс со stateless ML API и остаётся
единственным владельцем состояния сессии. Браузер не получает полный `TurnRequest`,
ключ LLM или `SERVICE_AUTH_TOKEN`.

Backend загружает анкету `AGE_6_9`: D1 и D3 приходят как технический контекст,
а 12 содержательных вопросов передаются в ML API с исходными формулировками.
Перед первым ответом ребёнок выбирает последовательные вопросы или короткий
свободный рассказ. Выбор обрабатывается локально и не вызывает языковую модель.
Сессии хранятся в памяти одного процесса, последовательно обрабатываются под
отдельными блокировками и удаляются после периода бездействия.

## Настройки

Backend читает корневой `.env` и использует следующие переменные:

- `SERVICE_AUTH_TOKEN` — обязательный Bearer-токен для вызова ML API;
- `ML_TURN_URL` — endpoint обработки хода, по умолчанию
  `http://127.0.0.1:8000/v1/turns/process`;
- `ML_TIMEOUT_SECONDS` — ожидание ответа ML API, по умолчанию 200 секунд;
  подключение, отправка запроса и ожидание свободного соединения ограничены
  отдельно 10 секундами;
- `ML_RESPONSE_MAX_BYTES` — предел ответа ML API, по умолчанию 256 КиБ;
- `BACKEND_MAX_REQUEST_BYTES` — предел JSON-запроса браузера, по умолчанию 16 КиБ;
- `BACKEND_SESSION_TTL_SECONDS` — скользящий TTL сессии, по умолчанию 3600 секунд;
- `BACKEND_MAX_SESSIONS` — максимальное число активных сессий, по умолчанию 1000.

Токен не должен добавляться в переменные `VITE_*`, JavaScript или браузерные
запросы. Backend сам устанавливает `Authorization: Bearer ...` на соединении с ML
API и не следует HTTP-редиректам.

Один ход может последовательно вызвать модель до трёх раз: основной ответ,
исправление и проверка выбора после уточнения. Стандартные 200 секунд на ожидание
ML API покрывают три вызова по 60 секунд и 20 секунд на обработку. Если
`LLM_TIMEOUT_SECONDS` в ML API увеличен, задайте `ML_TIMEOUT_SECONDS` больше
`3 × LLM_TIMEOUT_SECONDS` с запасом на обработку; верхняя граница настройки
backend — 390 секунд.

Обычный HTTP разрешён только для loopback-адреса. Настраиваемый URL должен вести
точно на `/v1/turns/process`; для удалённого ML API требуется HTTPS.

## Локальный запуск

Сначала запустите ML API на порту 8000, затем во втором PowerShell 7 из корня
проекта:

```powershell
.\Backend\scripts\Start-Backend.ps1
```

Backend слушает только `127.0.0.1:8001`. Для автоматического перезапуска при
разработке доступен параметр `-Reload`.

Публичные маршруты:

- `POST /api/sessions` с `{ "age": 8, "respondentMode": "CHILD" }`;
- `GET /api/sessions/{sessionId}`;
- `DELETE /api/sessions/{sessionId}`;
- `POST /api/sessions/{sessionId}/dialog-mode` с `messageId`, `stateVersion` и
  `dialogMode`, равным `GUIDED` или `FREE_STORY`;
- `POST /api/sessions/{sessionId}/messages` с `messageId`, `content` и
  `stateVersion`.

`messageId` является ключом идемпотентности. После успешной фиксации повтор той же
команды возвращает текущий снимок без нового вызова ML API. После отказа точно ту
же команду можно повторить с прежним ID. Повтор ID с другим содержимым и команда к
устаревшей `stateVersion` получают HTTP 409. При сетевом, протокольном или
предметном отказе ML API пользовательская реплика и патч не фиксируются, но связь
ID с исходной командой сохраняется. После свободного рассказа Backend разрешает
ML-сервису предложить ответы только для исходно незаполненных вопросов; Core
проверяет каждый элемент патча. После проверки Core Backend сохраняет переданный
`assistantReply`. Контроллер собирает его из короткой живой подводки и дословного
текста следующего официального вопроса. Для действия `CLARIFY` Backend сохраняет
контекстный `clarificationText`: он должен точно
совпадать с `assistantReply`, содержать один короткий тематический вопрос без ссылок,
разметки, чувствительных запросов и дословного повтора. Первое уточнение может быть
сформулировано живым разговорным языком и включить
до двух проверенных безопасных терминов из ответа ребёнка, например «манга» и
«комиксы», чтобы не
терять контекст разговора. Состояние накапливает
`contextMessageIds`, поэтому следующее решение агента получает всю цепочку ответов,
приведших к уточнению. Итоговый ответ обязан сослаться ровно на эту цепочку и
текущую реплику; публичное `evidence` показывает соединённые дословные фрагменты.
После двух смысловых уточнений новое смысловое уточнение не задаётся. Технический
`REASK_QUESTION` может повторить активный вопрос без изменения баллов и счётчика
уточнений; Backend сохраняет реплику ребёнка в истории и контексте. Если ясного
ответа по-прежнему нет, для `SCALE_0_3` сохраняется автоматический `0/3` с
`origin=POLICY_DEFAULT` и `defaultReason=CLARIFICATION_LIMIT_REACHED`, без
пользовательского `evidence`. Для остальных типов вопросов проверенный
`SKIP_QUESTION` с причиной `NO_ANSWER_AFTER_RETRY` завершает вопрос без оценки.
Публичный снимок отличает автоматический ноль и служебный пропуск от явной просьбы
ребёнка пропустить вопрос.
Определение анкеты отдельно задаёт политику минимального числа уточнений: для M1
ответ «не очень люблю такое» сохраняется как `1/3` и ведёт к следующему вопросу,
не вызывая дополнительного расспроса об умении. Для S4 любовь к названным видам
изображений, например манге и комиксам, сохраняется как `2/3` без вопроса о деталях.

Текущее in-memory хранилище подходит для локальной сквозной проверки одним
backend-процессом. Для нескольких процессов интерфейс репозитория нужно заменить
общей БД с транзакционной проверкой версии.

Скрипт запуска привязывает Backend только к loopback. Перед публикацией `/api` во
внешнюю сеть нужны пользовательская аутентификация, привязка сессии к пользователю,
ограничение частоты и стоимости запросов, общий предел параллельных ML-вызовов и
постоянное хранилище. Идентификатор сессии нельзя считать заменой аутентификации.
